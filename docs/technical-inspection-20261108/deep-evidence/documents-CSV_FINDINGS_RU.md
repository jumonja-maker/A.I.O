# Глубокий осмотр CSV: точность и текстовые литералы

Основа: `660b47002672a3ad86e4ce8b1cd7c514df178295`, PR103. Изменения не коммитились дочерним агентом.

## Подтверждённое до исправления

Три сгенерированных UTF-8 CSV загружены и преобразованы текущим Guard adapter через реальный Linux LibreOfficeDev 26.8.0.0.alpha0. Результат XLSX независимо прочитан openpyxl и через raw worksheet XML. Хеши источников неизменны. Каждая операция заняла 7.1–7.7 сек.

* `CustomerID=12345678901234567` стал числом `12345678901234600`. `99999999999999999` стал `1e17`. Все поля в кавычках `QUOTE_ALL` не помогали: старый импорт сохранял только явно подсказанные ведущие нули второго столбца, а первый столбец округлял.
* CSV-текст `=1+1` стал ячейкой с типом `f`, а не буквальным текстом. Одного совпадения строкового значения недостаточно: тип меняет вычислительный смысл.
* `1E10` превратился в число, `01/02/2025` и `2025-03-04` — в даты. Это отдельно зафиксировано как неоднозначность автоматического разбора нетипизированного CSV, а не автоматически объявлено дефектом.
* В старых receipts `warnings=[]`; для длинных чисел/формулоподобных литералов не было resultCheck. В QUOTE_ALL примере проверка csv_text_ids давала checked_subset только для сохранённых ведущих нулей, не для округлённого CustomerID.

Это сочетание ограничений/стандартной политики числового импорта Calc и отсутствия превентивной защиты в AIO. Оно не доказывает отдельный новый дефект LibreOffice и не означает, что Excel умеет без ограничений хранить такие числа как числовые значения.

## Точечное исправление AIO

Общая классификация чувствительных CSV-токенов используется и для подсказки импортёру, и для независимого source↔output контроля. Помимо ведущих нулей защищены ASCII decimal/exponent токены с более чем 15 значащими цифрами мантиссы и буквальные значения со знаком `=` после начальных пробелов. Важны точная строка и string cell type; формула с тем же строковым представлением отклоняется.

Из sample ограниченного 256 строками и 64 KiB выбираются только чувствительные столбцы с Text type 2. Остальная книга не принудительно переводится в текст. Если в одном столбце присутствует чувствительное значение, другие значения этого столбца также могут стать текстом; пользователь получает явное предупреждение. Обычные даты/scientific с ≤15 цифрами в нечувствительных столбцах сохраняют прежнюю native inference policy. Глобальный EvaluateFormulas не менялся.

Для XLSX/XLSM/XLTX/XLTM полный ограниченный source scan независимо проверяет чувствительные координаты и типы результата, включая поля за пределами sample. Если поздний риск не попал в подсказку и native испортил значение, результат отклоняется ENGINE_OUTPUT_CONTENT_LOSS. Успешный receipt содержит candidateKinds и сообщения CSV_HIGH_PRECISION_AS_TEXT/CSV_FORMULA_LITERALS_AS_TEXT. 

## Проверки и границы

10 новых тестовых методов: типы, знаки, decimal/exponent, кавычки, четыре разделителя, хвост после sample, четыре Excel-targets, неверный formula-type и исчерпание бюджета. До исправления — 18 behavioral failing subcases и 4 ошибки отсутствующих новых metadata fields. После — 135 целевых тестов PASS вместе со старыми CSV/DIF/recipe/legacy-sheet контрактами. Полные suites не запускались этим агентом.

Ничьи HTML/media файлы не менялись. Минимально изменены только CSV functions, блок распространения B29 warnings в adapter.py и строки WARNING_TEXT в export_recipe.py.

Границы: readback только для четырёх поддерживаемых OOXML Excel targets; неизвестный синтаксис, другие форматы, locale/grouping numeric grammar, overflow/underflow и полная семантика CSV не сертифицированы. Остались прежние inspection budgets (32 MiB / 100000 строк / 50000 tracked cells / 256 столбцов / 8 сек). Исчерпание даёт not_checked и явный CSV_TEXT_IDS_NOT_CHECKED, не новую глобальную размерную блокировку формата. Нельзя считать этот статус доказанной сохранностью. CSV source повторно сканируется при разных Excel targets, существующая стоимость этого пути отдельно не оптимизирована.

Native post-fix повтор завершён: все три контроля вернули точные исходные строки с типом s, без округления и исполнения формулы; warnings политики присутствуют, исходники неизменны. Проверены также все строки дат/scientific в смешанном чувствительном столбце: они честно стали Text. Время составило 15.248/12.060/12.404 сек против исходных 7.734/7.085/7.388 сек. Это не изолированный benchmark CSV-политики: общая pipeline менялась другими агентами, источник разницы не установлен. Эти цифры переданы root и performance-аудитору, они не выдаются за улучшение скорости.

Артефакты: native_csv_probe.py; native-csv/evidence.json и raw worksheet XML внутри него; csv-regressions-before.log; csv-regressions-after.log; csv-compatibility-final.log; csv-change-evidence-index.json. Ранний csv-compatibility.log содержит ошибку командного harness — два несуществующих test-module имени — и не является ошибкой AIO.

## Официальный контекст LibreOffice

CSV format не содержит схемы типов. Официальный tracker #150635 RESOLVED/NOTABUG рекомендует Text type при импорте значений, исходная запись которых должна остаться текстом: https://bugs.documentfoundation.org/show_bug.cgi?id=150635 . Следовательно, новый порог >15 значащих цифр в AIO — консервативная политика сохранности конкретных токенов, а не утверждение, что любое 16-значное число невозможно хранить числом. Уже исправленные версии конкретных ошибок XLSX-save нельзя автоматически объявлять текущей CSV-регрессией.

Официальная грамматика CSV options: https://help.libreoffice.org/latest/en-US/text/shared/guide/csv_params.html . Token 5 задаёт типы столбцов (Text=2). Token 13 имеет важную совместимость: явно false/пустой означает текстовый импорт формул, но при полном отсутствии этого token формулы включаются для старых коротких options. Наблюдавшаяся строка AIO44,34,76,1 как раз не содержит token 13. Наш фикс сохраняет рискованные поля типом Text без изменения этой глобальной grammar.

Итоговый native evidence: native-csv-after/evidence.json + native-csv-after/assertions.json.
