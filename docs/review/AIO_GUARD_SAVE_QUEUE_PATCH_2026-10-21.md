## Какие проблемы исправляются вместе

### 1. Готовые результаты живой очереди можно сохранить в папку

Раньше backend отклонял `save_folder()` для работающего задания, а список доступных результатов исключал такие задания. Теперь он предоставляет снимок уже завершённых выходных файлов. Он не включает открытые файлы текущего экспорта.

Пример: первый PDF готов, второй документ конвертируется, третий ожидает. Пользователь сохраняет первый PDF; очередь продолжает работу. Файлы, появившиеся во время копирования, не получают подтверждение сохранения. Повторное сохранение после завершения может скопировать полный набор в новую папку.

У задания есть отдельная блокировка сохранения и I/O lease. Два сохранения одного задания одновременно отклоняются с `SAVE_BUSY`. ZIP доступен после завершения очереди. Удаление результатов из панели также требует завершить или явно отменить работающую очередь.

### 2. Сохранение больше не означает автоматическую остановку задания

Клиент раньше вызывал `/release` после любого успешного сохранения. Для живого задания освобождение связано с остановкой, поэтому такую операцию нельзя применять к частичному снимку.

Теперь клиент проверяет явное `savedAll`, факт завершения снимка и принадлежность задания активной операции. Снимок работающей очереди не вызывает `/release`, `/cancel` и сброс основного интерфейса через `aio-guard-saved`. Даже если очередь закончилась во время диалога сохранения, подтверждение не удаляет задание раньше, чем ожидающий клиент обработает его конечный статус. В этом пограничном случае результат остаётся доступным до следующего сохранения или явного удаления.

### 3. Временная ошибка чтения статуса не отменяет конвертацию

Раньше исключение из GET `/jobs` могло завершить клиентскую операцию и привести к `/release` из `finally`. Теперь транспортные ошибки, ошибки JSON, HTTP 408/429/5xx и потеря базы дельты повторно запрашивают состояние. Пауза между последовательными попытками растёт до пяти секунд; новые потоки и повторные экспорты не создаются.

При расхождении базы дельты клиент получает полный снимок. Более старый ответ опроса не перезаписывает состояние, которое уже подтвердил ответ на команду. Подтверждённое состояние `/start` становится исходной базой наблюдения.

Ошибка чтения статуса сама по себе не разрешает удалять или останавливать живое либо неоднозначно запущенное задание. При постоянной ошибке авторизации или исчезнувшем задании автоматическое восстановление наблюдения не обещается. Это ещё не полноценный supervisor UI/backend.

### 4. Команды очереди имеют явный результат

Ответы паузы, пропуска и отмены сразу применяются к нужному заданию. Отказ отмены не выдаётся за успех. Пропуск без определённого текущего файла, повтор ошибок во время другой операции и повтор без ошибок возвращают понятную причину.

В панели кнопка остаётся заблокированной до ответа, включая промежуточные перерисовки. Пользователь видит выполнение, принятие команды или ошибку. Готовые результаты обнаруживаются и в уже открытой панели после появления первого выхода.

## Изменения сохранения и нагрузки

- `/saved` принимает необязательное `compact: true`. Ответ содержит идентификатор задания, число подтверждённых и оставшихся выходов, `savedAll`, `jobRunning` и состояние журнала. Он не сериализует повторно все файлы и задачи. Старый ответ по умолчанию сохранён для совместимости.
- Запись подтверждения в журнал вынесена из непосредственного удержания общего state lock. Это проверено блокирующей имитацией записи для завершённого задания. Другие записи worker в журнал пока могут выполняться под общим lock; полное устранение дискового I/O из блокировок этим патчем не заявляется.
- Копирование остаётся потоковым: блоки по 64 KiB, без загрузки полного результата в память. SHA-256 вычисляется при копировании; повторного сканирования всех файлов в приложении нет.
- Сигналы прогресса в Qt ограничены примерно десятью в секунду; конечный счётчик отправляется обязательно. Это ограничивает поток уведомлений при множестве маленьких файлов. Нативный диалог на Windows пока не проверен.
- В папке создаётся `AIO-save-status.json`: `writing`, `completed`, `cancelled` или `failed`, с `saveId`, ревизией снимка, числом выходов и байтами. `completed` означает завершение именно снимка. Полный состав снимка и состояние задания на его начало записаны в `AIO-results-manifest.json` схемы 2.
- `readbackVerified: false` указывает, что приложение не выполняло независимое повторное чтение накопителя. Хеш при записи не объявляется проверкой качества документа или гарантией физической записи носителем.
- При ошибке диска или отмене незавершённый снимок не подтверждается. Исходные результаты остаются у Guard, временные `.aio-part-*` удаляются; внешняя папка может содержать уже скопированные файлы и признак незавершённого сохранения.
- BlackBox получает `save_started` и `save_failed` через существующий неблокирующий emitter. Схема полей и код BlackBox не меняются.

## Как воспроизвести

В полном checkout с зависимостями проекта:

```sh
python -m unittest discover -s tests -p 'test_*.py'
node tests/guard_bridge_contracts.mjs
node tests/guard_save_queue_v09.mjs
python tools/qa/guard_v09_save_queue_acceptance.py --output /absolute/path/to/new-owned-qa-directory --executable /absolute/path/to/soffice
```

Последняя команда создаёт собственные синтетические документы и каталоги. Windows-проверку выполняет владелец отдельно на согласованном SHA; патч не запускает её автоматически.

Для практической приёмки нужны: сохранение во время обработки, отмена только сохранения, нехватка места на диске назначения, окончание очереди во время открытого диалога, повтор сохранения, пауза/пропуск/отмена на соседних задачах, восстановление после перезапуска и проверка независимости Excel. Во всех случаях завершённые исходные результаты должны оставаться доступны до подтверждения полного сохранения или явного удаления.

## Что остаётся следующим ящикам

1. Экспортные контракты: пустые HTML, TAB/TSV с неверным разделителем, дубли JPEG и расширение/тип контейнера. Исправления должны сравниваться с прямым запуском той же сборки LibreOffice, без массового запрета работающих направлений.
2. Скорость: измерить отдельно импорт, экспорт, запуск процесса и упаковку на одинаковом корпусе; затем повторное использование нативного документа и ограниченный пул изолированных workers. Не вводить параллельность до проверки отмены, профилей, памяти и принадлежности выходов.
3. UI больших очередей: убрать остаточные перекрытия индикаторов/кнопок и проверить 1000 файлов настоящим DOM/Qt. Одного Python heap замера недостаточно для вывода об утечке всей программы.
4. Точная диагностика зависания: получить стеки GUI/backend, CPU/RSS дерева LibreOffice, очередь Qt и последние принятые команды. Этот патч закрывает найденные пути остановки/рассинхронизации, но не доказывает первопричину зависания в пользовательском запуске.
5. Отдельный полный прогон корпуса после интеграции: принадлежность каждого выхода `jobId/fileId/format`, счётчики, форматы и сохранение. Advanced, сканер до/после и новые движки в эту приёмку не включать.

Это первый завершённый ящик по конкретной группе проблем. Он не заявляет исправление всех потерь качества, совместимости форматов или всей низкой скорости конвертации.
