# Guard: точнее проверять исходники, не добавляя тяжёлых проходов

Дата: 26.10.2026. Отдельный патч поверх `build/guard-v21-windows-nikita-20261026`,
коммит базы `266a33a161fd5348a7d1dcf89bf27ec6d4ef6cee`.

**Область:** структурная проверка исходного файла перед native-импортом.
Не новый конвертер, не анализ «до/после», не проверка визуального качества.
Меняется один продуктовый файл: `app_backend/converter_guard/source_contract.py`.
Слияние в main, сборка EXE, изменения движка и существующих workflows не выполнялись.

## Что изменено

1. XML-заголовки проверяются потоковым Expat без построения дерева содержимого.
   Первый блок — до 4 КиБ вместо прежних 64 КиБ. Чтение прекращается при получении
   нужного корня или типа тела ODF. Для flat XML повторно используется уже прочитанный
   префикс. Архивные изображения, листы и остальные ресурсы для этой проверки не читаются.
2. UTF-16 LE/BE теперь распознаётся в ODF, flat ODF, OOXML metadata и основном XML.
   Длинный XML-комментарий перед документом больше не скрывает тип flat ODF.
   Корни standalone MathML, SpreadsheetML 2003 и WordML 2003 задают ожидаемую native-модель.
   Эти дополнения не устанавливают новые импортёры LibreOffice и не подтверждают успешную конвертацию.
3. MIME основного компонента OOXML проверяется по точным известным значениям, а не
   по подстроке `ms-excel`/`wordprocessingml`. Незнакомые типы остаются непроверенными,
   а не объявляются испорченным XML. Известные Word/Excel/PowerPoint, шаблоны,
   macro-enabled declarations и Strict namespaces сохраняют проверку соответствия корня.
4. XLSB не передаётся XML-парсеру. Статус — `not_checked`, причина —
   `source_contract_binary_main`, ожидаемая модель — Calc. Ранее бинарный компонент
   попадал в XML-проверку: в частности, NUL приводил к общему статусу DTD/кодировки.
   Этот патч не утверждает, что BIFF12 полностью проверен, и не сертифицирует XLSB-конвертацию.
5. Парсер отличает реальные DTD/entity declarations от их буквального текста в комментарии.
   Реальные объявления не раскрываются: структурная проверка возвращает неопределённость.
   UTF-32 и неподдерживаемые кодировки также не объявляются доказанной порчей файла.
6. После неудачного чтения ODF content.xml можно проверить ровно его запись
   `encryption-data` в manifest. Зашифрованный контент, ZIP с паролем и недоступный
   алгоритм распаковки больше не обязаны превращаться в «повреждённый документ».
   На обычном ODF дополнительное чтение manifest отсутствует. Чужое пространство имён
   или запись о шифровании картинки не оправдывают сломанный content.xml.
7. Частый случай простых ASCII-путей OPC обрабатывается без полной URI-нормализации.
   Для Unicode, percent escapes, dot segments и специальных символов остаётся прежняя
   строгая логика. Дубликаты и неоднозначность main part, внешняя основная связь,
   выход за корень, неправильный namespace и конфликт MIME/корня по-прежнему отклоняются.
8. Отмена учитывается даже на обычном TXT; малый/исчерпанный бюджет означает
   `not_checked`, а не повреждение. Ошибки deflate/EOF обрабатываются как структурные
   ошибки для распознанного контейнера, не вылетают непойманным исключением.

## Что означает решение Guard

| Наблюдение | Результат структурной проверки |
|---|---|
| Метаданные известного формата согласованы | `recognized`; native-импорт ещё обязателен |
| Известный MIME противоречит namespace/корню, неоднозначная основная часть | `invalid` |
| XLSB, неизвестный MIME, неподдерживаемая кодировка, шифрование, бюджет | `not_checked`; это не разрешение конвертации и не доказательство повреждения |
| Формат не относится к этой проверке | `not_applicable`; дальнейшее решение остаётся native-импорту |
| Пользователь отменил операцию | `GuardError(CANCELLED)` |

`source_model_matches` и `source_import_hint` не ослаблены. Для уже поддерживаемых
flat aliases по-прежнему обязательны установленный явный фильтр и совпадающая модель.
Новых запретов по расширению/числу страниц/размеру нет. Бюджет относится к диагностике,
не к допустимости конвертации. Нет межфайлового кэша доказательств, дополнительных
запусков LibreOffice, сетевых запросов или изменений исходного файла.

Проверка заголовка намеренно не является проверкой всего XML: порча после прочитанного
заголовка может здесь не выявиться. Native-импорт, проверки результата и отдельный
анализ сохранности не заменяются этим быстрым проходом.

## Выполненные проверки

и `evidence/guard-source-scan-v22-tests.log`.

Дополнительно сравнение прежнего и нового `_opc_part_key`: **60 038 входов**, seed
`20261026`, **0 расхождений** по результату и типу исключения. Это воспроизводимый

Проверены неизменность SHA-256 исходников, отсутствие чтения manifest/media на обычном
ODF, чтение не более 4096 байт XML-потока в простом случае, отсутствие второго чтения
flat-префикса, строгий бюджет, отмена, реальная ZIP password flag и контролируемые
ошибки распаковщика. Тесты намеренно используют минимальные структурные fixtures:
они не объявляются полноценными документами для native-конвертации.

## Воспроизведение на полном checkout

```sh
python -m unittest discover -s tests -p 'test_guard_source_scan_v22.py' -v
python -m unittest discover -s tests -p 'test_guard_source_contract_v20.py' -v
python tools/qa/guard_source_scan_v22.py --rounds 9 --iterations 10 --output scan-v22.json
```

Последняя команда получает старый scanner через `git show` и проверяет его blob SHA.
При shallow checkout нужно сначала получить базовый коммит либо передать
`--baseline-file` с точным исходным файлом базы. Модуль benchmark изолирует только
импорт пакета, не подменяя реализацию сканера. Второй unittest выше — рекомендуемая
интеграционная регрессия существующего пакета, **локально здесь не выполнялась**.

## Ограничения приёмки

Полный тестовый набор репозитория, native LibreOffice на Windows/Linux, FULLTEST,
сборка EXE/установщика и end-to-end время preflight этим патчем не сертифицированы.
Перед интеграцией в рабочую сборку нужны эти проверки на штатном Runner. Локальные
результаты относятся только к указанному структурному модулю и тестовым данным.

Справочные первоисточники для реализации:
[Python Expat](https://docs.python.org/3/library/pyexpat.html),
[ODF 1.2 Packages](https://docs.oasis-open.org/office/v1.2/os/OpenDocument-v1.2-os-part3.html),
[XML 1.0](https://www.w3.org/TR/xml/).


## Независимый технический review 00AIO и Windows QA

После первоначального Draft проведён отдельный разбор реальных OOXML MIME из корпуса
85 форматов × 8 уровней и исходников LibreOffice. Он выявил **подтверждённый пропуск
DOTM**: настоящий основной тип Word-шаблона с макросами —
`application/vnd.ms-word.template.macroEnabledTemplate.main+xml`, а не
`application/vnd.ms-word.template.macroEnabled.main+xml`. В исходном PR такой
файл получал `not_checked` вместо `recognized`, ослабляя проверку ожидаемой
Writer-модели. Исправлена только точная таблица типов; добавлен тест успешного
распознавания и отрицательный контроль вымышленного имени MIME.

Первый общий Windows-прогон дополнительно выявил одно устаревшее ожидание
в тесте v16. Прежняя проверка требовала `not_checked` для ZIP-пакета с
UTF-16 flat-ODF корнем `office:document`. Теперь scanner читает UTF-16 и
доказывает, что пакетный ODF обязан использовать `office:document-content`.
Контроль уточнён в двух направлениях: неверная смесь имеет `invalid`,
корректный упакованный UTF-16 ODF — `recognized`. Защитная политика не
ослаблялась для того, чтобы сделать старый тест зелёным.
