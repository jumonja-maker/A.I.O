# A.I.O / Guard — мешок: ложные или недостаточно объяснённые пропуски маршрутов FULLTEST

**Дата обнаружения:** 25.10.2026  
**Трекер:** https://github.com/jumonja-maker/A.I.O/issues/57  
**Режим:** P1 / только сбор багов и подготовка следующего патча / без правок исполняемого конвертера / не MAIN.  
**Видимый симптом:** в списке загруженных файлов значок ⊘ и подпись «Не конвертировался: нет подтверждённых направлений Guard».  
**Область:** часть исходников FULLTEST-корпуса до 510 файлов; скриншоты показывают только 25 **разных имён**, не окончательное число.

## 0. Триаж: корректная блокировка не является багом Guard

**Решение владельца:** перед будущим патчем убрать из *очереди исправлений конвертера* все ожидаемые защитные отказы. Не удалять исходные файлы, наблюдения, коды причин и отрицательные регрессии. Система «До/После» от WORK занимается **качеством уже созданных результатов**, а не допуском источников, которые Guard не разрешил конвертировать.

Статус приведён ниже только по источникам и проектным регрессиям. **Ни одной ложной блокировки Guard по одним скриншотам пока доказать нельзя.**

| Группа | Точные исходники | Статус и действие |
|---|---|---|
| **Исторически ожидаемый защитный отказ: 2** | `05_LEVEL_2.fodt`, `05_LEVEL_2.fodp` | Старый QA явно использует их как отрицательные образцы с конфликтующим MIME. **Не создавать исправление Guard только ради их конвертации.** Окончательно исключить из активной очереди дефектов **после сверки SHA-256 текущего образца** с известным negative fixture и его `SOURCE_CONTAINER_INCONSISTENT`. Оставить тест, объясняющий отказ. Если байты/причина отличаются — вернуть в диагностику. |
| **Потенциально неполный комплект HTML: 4** | `02_LEVEL_2.htm`, `02_LEVEL_2.html`, `03_LEVEL_3.htm`, `03_LEVEL_3.html` | По прежнему FULLTEST L2/L3 имели недостающие PNG. **Не чинить Guard отключением проверки ресурсов.** Проверить точные HTML и относительные ссылки; при подтверждении недостающих PNG считать правильной защитой, но пометить потребность в восстановлении тестовых ресурсов. Если всё приложено и прямой LO работает — исследовать ложный отказ. |
| **Причина не установлена: 19** | 5 XLSX, 5 ODF, 4 PowerPoint, 3 DOCM/DOTM/DOTX, 1 SXW, 1 XLSM | **Не записывать как подтверждённые баги.** Сначала получить `nativeRoute`, `preflight.code`, выбранный target и прямое сравнение с LibreOffice. Часть может быть правильными отказами из-за native export filter или исходного контейнера. Исправлять только доказанный ложный отказ на *конкретной* паре источник → target. |

**Текущий баланс скриншотов:** 25 наблюдений = 2 *условно исключаемых* по известным negative fixtures + 4 *условно ожидаемых* из-за ресурсов + 19 *не классифицированных*. Это **не** означает, что осталось 19 доказанных ошибок. Проверка оригинального корпуса и контрольных SHA ещё не выполнена.

### Где проходит граница с модулем WORK «До/После»

- **Guard (до запуска)**: структурная проверка и настоящий native import, наличие необходимых HTML-sidecars, модель документа, наличие подтверждённой пары source → target, отмена и честное объяснение отказа. Нельзя обходить это для увеличения статистики успехов.
- **Converter + Guard (во время/после)**: действительный экспорт и сохранённый ненулевой результат; ошибки `ENGINE_OUTPUT_MISSING`, `PREFLIGHT_ROUTE_UNDETERMINED` и подобные не преобразовывать в `ready`.
- **WORK «До/После» (после фактического создания результата)**: проверка сохранности текста, изображений, формул, таблиц, страниц, макросов и оформления; в обнаруженных потерях разбираться отдельным модулем. У модуля нет «после», если конвертация не была начата.
- **UX остаётся зоной Guard**: вместо общей подписи «Нет подтверждённых направлений» раскрывать точный код, недостающие зависимости, выбранный target и безопасный следующий шаг. Даже корректная блокировка может быть плохо объяснена пользователю.

**Принцип будущего патча:** исправлять только проверенную *ложную блокировку*, а не все `skipped` подряд. При подтверждённом ожидаемом отказе закрывать именно *инженерную задачу на разблокировку* как `not_a_bug/expected_guard_rejection`, оставляя negative-образец и точную диагностику в отчёте. Если нет независимого native-доказательства успешной конвертации того же target — исправление маршрута не санкционировано.

## 0.1. ORP — отдельная ситуация: недоступный **целевой формат**, а не ошибочный skipped-исходник

**Новый ввод владельца:** в запущенном FULLTEST с 510 файлами / 87 целевыми форматами строка **ORP — ODF Database Report** показывает `Недоступно`. Это не равно значку ⊘ на исходном файле и не означает, что какой-либо из 510 был ошибочно исключён из прочих маршрутов.

**Проверка оригинальной Google Drive-папки** `1wxYCJklFTYiNiMTRyf699OmqoUMfGLmf` (25.10.2026): 510 непосредственных файлов, **85 разных расширений, по 6 экземпляров каждого**; **0 `.odb` и 0 `.orp`**. Папка: https://drive.google.com/drive/folders/1wxYCJklFTYiNiMTRyf699OmqoUMfGLmf

**Проверка точного upstream-фильтра LibreOffice:**
- `filter/source/config/fragments/filters/StarBaseReport.xcu` объявляет `StarOffice XML (Base) Report`, флаги `IMPORT EXPORT OWN DEFAULT 3RDPARTYFILTER NOTINFILEDIALOG`, но **DocumentService = `com.sun.star.report.ReportDefinition`**, а не Writer/Calc/Impress/Draw/BaseDatabaseDocument. https://github.com/LibreOffice/core/blob/master/filter/source/config/fragments/filters/StarBaseReport.xcu
- Тип `StarBaseReport.xcu` регистрирует расширение `.orp`, MIME `application/vnd.sun.xml.report` и `private:factory/sreport*`: https://github.com/LibreOffice/core/blob/master/filter/source/config/fragments/types/StarBaseReport.xcu
- Официальная справка: информация о созданных отчётах хранится **в файле базы данных LibreOffice Base**; пользователь создаёт/редактирует их через Report Builder, а готовый отчёт выполняется и открывается как документ Writer: https://help.libreoffice.org/latest/en-GB/text/shared/guide/data_report.html
- `app_backend/converter_guard/routes.py:route_reason` кодирует `NATIVE_REPORT_EXPORT_UNAVAILABLE` при отсутствии экспортёра `.orp` в **установленном** реестре и `NATIVE_DOCUMENT_SERVICE_MISMATCH` при наличии экспортёра, но отсутствии общей модели. Нельзя смешивать эти причины. Сама upstream-запись с флагом EXPORT **не доказывает**, что комплект LO на NIKITA имеет работающий standalone ORP-export.

**Предварительный вердикт:** недоступность ORP **ожидаема для набора, не содержащего отчётных моделей**, и не является доказанным багом Guard. Даже дополнительный `.odb` сам по себе **не создаёт** модель `ReportDefinition`; нужен реальный отчёт Base и native proof именно этого сервиса. В связи с этим **не надо отключать Guard или форсировать ORP** ради 1/87 дополнительных форматов.

**Оставшаяся проверка только если понадобится ORP-совместимость:** read-only NIKITA: записать `native.filters['StarOffice XML (Base) Report']`, `native.exports.get('orp')`, `native.import_services`, `registeredExport`, и значение `unavailableReasons['orp']` у одного типичного DOCX/XLSX и реального отчёта Base. Если реальный Base ReportDefinition доказан и штатный экспорт создаёт валидный ORP, но Guard блокирует **ту же пару**, это отдельный реальный баг. Без нативного доказательства считать ORP «специальный Base-формат / для данного набора нет подтверждённых маршрутов». Возможное UX-улучшение: показать эту конкретную причину рядом с `Недоступно`, без изменения допуска.

## 1. Что доказывают скриншоты

Реальная UI-подпись берётся из `addons/file-converter/aio-file-progress.js` при `data.state === 'skipped'`. В `src/converter-bridge.js` исходник может попасть в `unplanned`, когда среди **выбранных пользователем целевых форматов** у него нет подтверждённых `verifiedFileIds`. Тогда интерфейс показывает `skipped`.

Это доказывает **отсутствие запланированного подтверждённого направления** на момент проверки, но НЕ доказывает:
- что данный файл вообще не может быть открыт установленным LibreOffice;
- что для него не существует *никакого* возможного целевого формата;
- что LibreOffice запустил экспорт и ошибся;
- что любой из скриншотов свидетельствует о повреждении файла.

Без `report`, `nativeRoute`, выбранного `formatId` и конкретного `preflight.code` **причина каждого пропуска ещё не установлена**.

## 3. Не смешивать ожидаемые negative и реальные ложные отказы

- `05_LEVEL_2.fodt` и `05_LEVEL_2.fodp` фигурируют в `tools/qa/guard_v16_bugbag_acceptance.py` в `negative_controls()`: проверяется именно отказ `source_contract` для известных противоречивых Flat ODF MIME. Исходные файлы не исправлять и не разблокировать просто ради PASS. Для позитивных конвертаций генерировать **новые корректные образцы отдельно**, используя нативный LO и прямое повторное чтение.
- Устаревший `SXW` проверяется на согласованность StarOffice MIME и пространств имён ODF. Старый отрицательный контроль — `05_LEVEL_2.sxw`; показан **другой** `04_LEVEL_1.sxw`. Нельзя без проверки переносить на него статус «заведомо повреждён».
- Предыдущая QA документация (`docs/review/AIO_GUARD_V15_FULLTEST_PATCH_2026-10-23.md` и Issue #26) подтверждает наличие ссылок HTML/HTM L2/L3 на отсутствующие PNG-компаньоны. Проверить точное совпадение этих четырёх имён с теми HTML-источниками; не отключать path/dependency Guard. Без комплектующих файлов нельзя обещать полное сохранение страниц.
- Для пяти `.odf` не объявлять Writer/Calc по суффиксу: это может быть отдельная Formula-модель; проверять `DocumentService` из фактического содержимого и реестра.
- Для XLSX, XLSM, DOCM/DOTM/DOTX и PowerPoint template/show/macro проверить реальные Office Open XML `[Content_Types].xml`, главный part, отношения, фильтр импорта и настоящий контент VBA. Отсутствие `vbaProject.bin` — повод не обещать проверку сохранности макросов, но не причина угадывать блокировку.
- Никакой глобальной отмены Guard, фиктивного статуса `ready`, пропуска `preflight` или автоматического разрешения по расширению.

## 4. Карта диагностики будущего патча

**Ящик A — восстановление фактов.** Для 510 исходников собрать полный `conversion-report`, status snapshot, выбранные целевые форматы, имя + hash/размер оригинала, source SHA приложения и LibreOffice, `sourceContract`, `preflight.state/code`, `registryFingerprint`, `selectedImportFilter`, `documentServices`, `unavailableReasons`; отдельно подсчитать «не запланировано», «источник не распознан», «контейнер противоречив», «запущен экспорт и упал».

**Ящик B — прямой native-контроль.** Для каждого из 25 (и других по итоговому manifest) проверить **точно заявленные целевые форматы**: импорт и экспорт через установленный LibreOffice с частным профилем и подтверждённым установленным фильтром. Не путать способностью LO открыть источник с наличием LO-фильтра именно этого результата.

**Ящик C — ложные `skipped`.** Если прямой native LO проходит, а Guard нет, сравнить выбранный import filter, `modelLoaded`, `expectedServices`, `source_model_matches`, registry/overlay snapshots, `native.observed_decision`, frontend `eligible` и `plan`. Пропуск должен иметь точный технический код и понятное пользователю объяснение.

**Ящик D — fixture health.** Исторические corrupted Flat ODF/SXW и пропущенные HTML sidecars оставить отрицательными тестами по конкретному SHA; рядом добавить валидные L1/L2/L3 native-положительные образцы с контрольными маркерами и нативным повторным открытием. Не редактировать оригиналы пользователя.

**Ящик E — проверка качества.** После исправления: targeted NIKITA Windows на группах, отсутствие ложного `ready`, честные ошибки, корректный UI badge, per-target `resultChecks`, сохранение байт и source/readback SHA, отмена и восстановление. Только затем полный FULLTEST-510 / BLACK.BOX и проверка качества полученных файлов.
