## Что исправлено дополнительно к WORK

1. Windows-процесс создаётся с CREATE_SUSPENDED. До запуска его кода выполняется AssignProcessToJobObject. Затем принадлежность проверяется, возобновляется единственный принадлежащий процессу первичный поток и только после этого вызывается startup callback. Это закрывает окно между запуском venv/другого bootstrap и привязкой родителя к Job Object.
2. Нулевой счётчик ActiveProcesses не выдаётся за сигнал завершения всех захваченных процессов. До TerminateJobObject фиксируются дескрипторы текущих членов собственного Job Object, после него проверяются и счётчик, и сигнал завершения каждого удержанного дескриптора. PID reuse, чужая принадлежность и ошибка API не принимаются как подтверждённая остановка.
3. Частный короткий профиль и owner marker сохранены. Фабрика получает ещё не созданный дочерний путь. Профиль удаляется только после подтверждённой остановки; пользовательские исходники, внешние сохранённые файлы и чужие LibreOffice-процессы не входят в cleanup.

Важная граница: механизм не является доказательством остановки произвольных внешних процессов, запущенных обходным API. Он управляет собственной ограниченной деревом Job Object нативной сессией. При невозможности доказать остановку возвращается ошибка/неопределённость, а не утверждение об успехе.

## Основание использования Win32

Документированные операции: Microsoft Learn `AssignProcessToJobObject`, `ResumeThread`, `TerminateJobObject`, `WaitForSingleObject`. Последовательность suspended → assignment → resume соответствует официальному примеру Microsoft: https://devblogs.microsoft.com/oldnewthing/20230209-00/?p=107812 . Нативная Windows-проверка, а не только документация, является основанием приёмки.
