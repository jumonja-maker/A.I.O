# A.I.O — M04: независимая история завершённых конвертаций

Дата: 30.10.2026. База: `25712d9bc2a0cc25df8fdb52f2670593f451ac1a`.
PR #83, `fix/fulltest-critical-hosted-lo-20261029`. MAIN и базовая QA-ветка не меняются.

## Пользовательский сценарий

В окне «Состояние» появился отдельный раскрываемый раздел «История завершённых конвертаций».
Он показывает дату записи, первый исходник, количество исходников, успешных и неудачных
операций, число сохранённых выходов. Полный JSON-отчёт скачивается по отдельной кнопке.
Есть обновление списка, переходы назад/вперёд и подтверждаемое удаление отдельной записи.

История хранит отчёты, а не документы. Удаление записи не удаляет исходники или результаты,
не подтверждает их сохранение и не освобождает задание. Очистка временных результатов,
включая explicit discard, не удаляет уже записанный отчёт. Это не Recovery и не резервная
копия документов; старые результаты по записи истории восстановить нельзя.

## Хранение и интеграция

Новый `app_backend/converter_guard/conversion_history.py` использует стандартный sqlite3.
В штатном сервере база находится в `data_directory()/history/conversions.sqlite3`, отдельно
от `data_directory()/jobs`. Конструктор отвергает пересекающиеся корни истории и временных
результатов. Для тестовых/custom Recovery-путей история не включается без явного параметра
`guard_history_parent`; старый конструктор ConverterGuard остаётся совместимым.

Конструирование и чтение пустой истории не создают каталог или базу. Снимок записывается
в конце рабочего задания, после повторной упаковки и на границе завершения сохранения.
Нет записи на каждом файле, задаче, тике прогресса или предварительном сканировании.
Метаданные отсоединяются под state-lock; JSON и SQLite I/O выполняются вне него.
Существующая I/O lease сохранения удерживается до завершения записи истории, чтобы
close() не завершал этот участок преждевременно. Новые потоки, импорты LibreOffice,
чтение исходников/выходов, OCR или анализ качества не добавлены.

SQLite-транзакции обновляют одну запись задания. Внутри поколения более старая или равная
ревизия не затирает новую. После настоящего восстановления задания его счётчик ревизии
начинается заново: перед публикацией восстановленной модели история связывается с новым
поколением. Запоздалый писатель предыдущего поколения больше не может заменить запись,
даже с большим старым счётчиком. Отсутствующий отчёт при такой привязке не объявляется
выполненной конвертацией и не появляется как фиктивная строка.

Удаление оставляет только внутреннюю отметку идентификатора. Это предотвращает возврат
записи от запоздалого сохранения или последующего Recovery. Не обещается криминалистическое
стирание байтов SQLite с носителя. Содержимое отчёта и сводка логически удаляются; файлы
конвертации не открываются. Автоматического удаления старых отчётов нет.

Эфемерные поля ticket/downloadUrl/previewUrl/token не сохраняются. История локальная и
содержит пользовательские имена файлов/диагностику; это не обезличенная телеметрия.

## Отказы и смысл статусов

Повреждённая/неизвестная база не перезаписывается и не выдаётся за пустую. Символьные ссылки
на корень/базу/журналы отвергаются; отсутствующий путь — нормальное состояние первого запуска.
Ожидание блокировки SQLite ограничено 0,5 секунды. Это не гарантия против всех изменений
файловой системы сторонним процессом с доступом к каталогу пользователя.

Ошибка истории не меняет успешность конвертации, подтверждение сохранения и владение
результатами. Текущий сеанс получает sticky `HISTORY_WRITE_FAILED`, видимый в истории.
Позднейший успешный write не стирает предупреждение, будто пропущенный отчёт восстановлен.
История не гарантируется при сбое диска/принудительном завершении до терминальной записи.

`historySnapshot` явно содержит scope, revision, sessionId и `containsResultFiles=false`.
Статус saved означает последнее наблюдение AIO, а не новое подтверждение существования
пользовательской копии на диске сейчас. Успешное сохранение не переписывает ошибку
конвертации или qualityCompared. Экспорт JSON истории через браузер не выдаётся за
независимо проверенную запись внешнего диска и не заменяет квитанцию ZIP-save M30.

## API и интерфейс

Все маршруты защищены существующим X-AIO-Token:
- GET `/api/converter-guard/history?limit=25&before=...` — только сводки;
- GET `/api/converter-guard/history/report?job=...` — один полный отчёт;
- POST `/api/converter-guard/history/delete` — только jobId и confirm=true.

API ограничивает страницу 50 записями, UI запрашивает 25. Курсор опирается на неизменный
порядковый номер, а не OFFSET: новые записи не сдвигают просматриваемую старую страницу.
Список не декодирует полные отчёты. Неизвестные/дублированные параметры и неправильные
идентификаторы отвергаются. Исторические методы не вызывают _get/_load_recovery.

`src/conversion-history.js` подключён перед `guard-queue.js`; существующий дизайнер и
элементы выбора форматов не заменяются. Нет фонового опроса. Запрос начинается при явном
раскрытии раздела или действии пользователя. Закрытие, pagehide и unmount отменяют запрос,
поздний ответ не рисует старую запись. Имена выводятся textContent, узлы ограничены текущей
страницей. Ошибка транспорта не стирает предыдущий список. Blob URL отчёта освобождается.

История разработки не скрыта: первый кандидат ошибался на отсутствующей базе, затем был

чтениях — добавлен closing без отключения проверок. Отдельно усилена защита поколения
восстановленного задания и добавлен реальный повторный save после reopen.

## Цена и пределы

Копирование метаданных, сериализация JSON и запись SQLite имеют стоимость, пропорциональную
размеру отчёта. Полный отчёт загружается в память только по запросу или при записи; база
растёт с историей. Нулевую стоимость и постоянную память для произвольного отчёта не обещаем.
Общий FULLTEST/performance benchmark не заменён короткими тестами.

История охватывает завершённые запуски и наблюдённые сохранения. Автоматическое восстановление
истории ранее удалённых сессий, потерянных отчётов после аварии до записи, поиск по всем
старым исходникам и запуск конвертации из исторической строки не реализуются этим блоком.
Визуальная приёмка установленного Windows-приложения, темы/DPI/малое окно остаётся открытой.

В продукт переносятся обычные исходники девяти проверенных файлов и этот документ, без
подготовительных скриптов/workflow/publisher. На момент подготовки документа полный CI
точного продуктового SHA ещё PENDING; итог фиксируется в PR после завершения Windows/Linux
и упаковки EXE. Пин LibreOffice 26.8.2.2 не меняется.

MAIN не изменяется; PR остаётся Draft. M16/M17, другие пункты мешка и исходный FULLTEST
200/5723 остаются открытыми. Исторические 1079 отклонений не пересчитываются.
