# A.I.O — A05: снять Excel merge_gate до HTTP-ответа

Дата: 30.10.2026. База: QA PR #83 SHA `a5cc6d4b31880c7ea2e36861f48b18080ad45621`. Отдельный QA-only патч; MAIN без изменений.

## Воспроизведённый регрессионный дефект

Интеграционный Windows CI [41090413225](https://github.com/jumonja-maker/A.I.O/actions/runs/41090413225) обнаружил одиночное падение `test_idle_upload_fails_and_next_complete_merge_succeeds` (исходный A05) в строгом полном suite. Успешный второй Excel /api/merge возвращал HTTP 200, но немедленная попытка нового приобретения `merge_gate` возвращала False. Причина установлена в сервере: `return self._send(200,...)` вызывался **внутри try**, а `merge_gate.release()` выполнялся в `finally` только после отправки HTTP-ответа. Точно так же была уязвима последовательность HTTP 408/400/500. Это настоящая гонка порядка ответа и освобождения, а не дефект теста.

## Продуктовый патч

- Владелец `merge_gate` полностью читает upload и подготавливает либо бинарный результат объединения, либо код ошибки.
- Gate освобождается **до первого байта** HTTP 200, 408, 400 или 500; никакой долгий upload или Excel merge не выполняется после его освобождения.
- `EXCEL_UPLOAD_IDLE_SECONDS` по-прежнему применяется только к чтению multipart, не к нормальной длительной операции объединения.
- При сетевом обрыве отправки готового ответа gate уже освобождён. Текст ошибки и публичные кодировки не меняются.
- Текущий socket-level тест дополнен перехватом реальной серверной `_send`: во время отправки HTTP 408 и HTTP 200 `merge_gate.acquire(blocking=False)` должен возвращать True. Послe успешного завершения по-прежнему проверяется повторная операция без перезапуска.
- Никаких изменений конвертера, Guard, интерфейса, раннеров, релизов или MAIN.
