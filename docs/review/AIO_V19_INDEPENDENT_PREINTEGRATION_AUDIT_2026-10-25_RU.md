**Назначение:** независимая проверка патча WORK для *последующего* объединения с мешком Guard. Никакая версия не интегрирована, не собрана заново и не перенесена в main в рамках этого аудита. Это source/review + сверка существующих Windows/Linux/Qt свидетельств; независимый запуск всей 792-test suite и полного FULLTEST-510 аудитом не выполнялся.

## Краткий вердикт

Модуль выглядит технически зрелым как **отдельная** разработка: исходники и исходные результаты не переписывает, analysis opt-in, ресурсоограниченные дочерние процессы, ограниченное чтение, SQLite, точные статусы \`checked/uncertain/not_checked/confirmed_loss/format_limitation\`, авторизованный локальный HTTP и проверенные native-повторы PDF/CSV.

Официальная машина сообщает SELFHOSTED SUCCESS #40197557880: 785/792 Windows (7 POSIX N/A), 763/792 Ubuntu (29 Qt/LO N/A); 792 уникальных теста на хотя бы одной среде. Не путать с интеграционной приёмкой новой общей ветки. Реальный Windows native LO проверял **два** ограниченных рецепта, а не 85 × 510. EXE проверен как упакованные worker/assets; **полный desktop UI + LibreOffice из EXE не запускался**. Замер 1000 небольших текстовых файлов 88,97 с — не массовая Office-конвертация.

**Интеграционное решение:** PR #54 нельзя переносить как набор полных файлов поверх Guard v18.2.1. Сначала решить находки ниже, вручную сверить пересечения и заново тестировать общий функционал.

## P1 — подтверждённый конфликт двух линий разработки

Точная база PR #54: \`3ca80cf40577372a4177f82939756247ecc95bfb\`. Рабочие v18.2/v18.2.1 исправления находятся на отдельной линии, функциональный source \`cbe404215203400df81c5ab88695173468e5b043\` (Draft PR #53/#56). GitHub сравнение показывает **diverged**; общие модифицированные файлы как минимум:

- \`app_backend/converter_guard/adapter.py\`
- \`app_backend/converter_guard/core.py\`
- \`app_backend/converter_guard/export_recipe.py\`
- \`src/converter-bridge.js\`
- \`src/guard-queue.js\`
- \`tests/test_converter_native_dom.py\`.

В v19 **нет** закреплённого реестра \`_bound_route_decider\`, отдельной стадии \`preflightPhase=routes\`, \`preflightMatrixCompleted/Total\`, кооперативной отмены матрицы и ограниченного CSV→DBF native CLI recovery \`NATIVE_DBF_CLI_RECOVERY\`. В v19 \`cancelInspection()\` не содержит ранее исправленного backend \`POST /cancel\`. Кроме того, v18.2 имеет ограничение обычного preflight до 15 с на исходник для больших пакетов, v19 — нет.

Это **не регрессия, внесённая WORK сознательно**: это разные source-линии. Но слепая замена файлов при объединении вернёт дефекты #50/#55 и прежнее 510/510-зависание. 

**Gate:** ручной трёхсторонний merge, preserve-adapter и cancel/route tests; затем real NIKITA 510 preflight, blue cancel during \`routes\`, CSV→DBF cold/warm+real Guard, source SHA, UNO same-model checks, и только потом интегрированная сборка.

## P1 conditional — неподтверждённый fingerprint восстановленного output может привести к ложному выводу

**Источник, достаточный для source-level воспроизведения:**

1. \`core.py:_Artifact.sha256\` по умолчанию \`None\`; \`core.py:_recover_results\` создаёт artifact с \`sha256=output.get('sha256')\`, а обязательная readback-проверка SHA выполняется **только если** поле не \`None\` (прибл. строки 597–607).
2. \`comparison_inputs()\` передаёт \`artifact.metadata()\` с возможным пустым \`sha256\`.
3. \`comparison_service.py:_worker\` строит \`sha256\` map, содержащую \`None\`.
4. \`comparison_worker.py\` при проверке результатов использует \`if expected and observed != expected\`; во втором проходе \`not pair['sha256'].get(name) or ...\`. Следовательно, для legacy output без сохранённого контрольного SHA отсутствие известной идентичности не блокирует анализ — результат может быть отнесён к исходной конвертации даже если его содержимое изменилось позже.

Это **условный реальный путь**, а не утверждение, что свежие v19 outputs не имеют SHA: свежие экспорты обычно записывают SHA, и существующие позитивные тесты его используют. Но модуль заявляет честную атрибуцию потерь и восстановление старых заданий — этот случай обязательно надо покрыть.

**Требуемое поведение:** если отсутствует проверенный ранее digest результата, показывать \`not_checked\`/«исторический результат без подтверждённого SHA», а не \`checked\` или \`confirmed_loss\` про исходный экспорт. Нельзя создать SHA *сейчас* и выдавать его за хэш, записанный после экспорта. Негативный тест: восстановленная запись с \`sha256=null\`, та же длина изменённого файла, запрос compare/preview/retry.

## P2 — неоднозначная сохранность истории после подтверждённого сохранения

\`src/converter-bridge.js:prepareInputs\` передаёт \`retainSources:true\` даже когда пользователь ещё не нажимал «До/После»; это осмысленная возможность сравнить позже, но нагрузка на хранилище растёт для каждого FULLTEST-исходника.

\`core.py:_prune(reap_saved=True)\` (вызывается при новом \`create\`) удаляет полностью сохранённые задания, если они больше не заняты. \`core.py:close()\` в recovery-режиме аналогично освобождает каталог задания после сохранения всех outputs. SQLite-отчёт и история \`comparison/\` лежат **в том же** каталоге. Получается, что сохранённый локальный отчёт «До/После» может быть удалён после следующей конвертации или перезапуска приложения, несмотря на постоянную историю в рамках *удерживаемого* задания.

Это может быть **запланированная политика очистки**, а не нарушение безопасности. Но UX должен честно различать «история пока пакет удерживается» и «постоянная история после сохранения». Принять решение: отдельное долговечное хранилище только маленьких метаданных, явный экспорт отчёта или предупреждение при удалении, без автоматического бессрочного удержания тяжёлых исходников.

**Тест:** analysis completed → сохранить все outputs → создать вторую конвертацию / закрыть AIO → открыть историю первого пакета. Задать ожидаемый контракт и проверить исходники/результаты/историю независимо.

## P2 — восстановление «последнего повтора» не привязано к текущему analysisId

В \`comparison_service.py:_recover()\` выполняется \`SELECT payload FROM retry_events ORDER BY seq DESC LIMIT 1\` **без** \`WHERE analysis=?\`, после чего результат присваивается \`item.retry\` текущему восстановленному сеансу. \`item.identity\` читается из актуального указателя \`current\`, тогда как \`retry_events\` сохраняют события нескольких сеансов.

При цепочке analysis A → retry A → explicit restart analysis B → relaunch приложение последняя попытка A может попасть в верхнее поле \`retry\` сеанса B. Общая **страничная история** всех попыток может и должна оставаться доступной; но текущая retry-панель не должна представлять попытку другого \`analysisId\` как активную для нового анализа.

**Тест:** completed A + retry → restart B → завершить B без retry → полностью перезапустить сервис → проверить, что \`snapshot(B).retry\` относится к B либо пуст, а \`retryHistory\` содержит исторический A с явной подписью.

## P2 — повреждённый catalog.sqlite отличается от повреждённого results.sqlite

Рестарт повреждённого индивидуального \`results.sqlite\` протестирован. Но если повреждён **\`comparison/sessions.sqlite\`**, \`_recover\` не может получить \`current\` из SQLite, а путь \`start(restart=True)\` вновь пытается прочитать тот же catalog до создания нового анализа. Возможен постоянный \`COMPARISON_REPORT_UNAVAILABLE\` вместо обещанного явного restart.

**Риск не подтверждён end-to-end на таком повреждении**, но последовательность вызовов показывает отсутствие отдельного восстановления самого каталогового индекса. Добавить направленный негативный тест: повреждённый \`sessions.sqlite\`, сохранённые exports, запрос restart — не уничтожать первое содержимое и не выдавать новое подтверждённое сравнение из старой повреждённой БД.

## P3 — ограниченное покрытие валидных одноколоночных CSV

\`comparison_analysis.py:_csv_summary\` требует в пробе минимум два столбца (\`len(sample[0]) > 1\`). Любой валидный CSV из **одной колонки** получает \`csv_dialect_not_determined\` и \`not_checked\`. Это честный, а не ложноположительный итог, поэтому не P1 и не повод отключать Guard, но значимая недоработка удобства «До/После».

Дополнить parser/test так, чтобы не угадывать диалект там, где разделителей нет: можно подтвердить текстовые значения как одноколоночные только при однозначных условиях, иначе оставить \`not_checked\`.

## Преимущественно положительные результаты проверки

- Не обнаружено обхода Guard: два конечных auto-рецепта (\`pdf_preserve_images\`, \`csv_preserve_values\`) зависят от установленного native filter, подтверждённой модели и явного выбора пользователя.
- Исходные результаты остаются независимыми от кандидата повтора; для новых файлов используются отдельные job IDs, проверяется source и parent output digest.
- Worker и preview отделены, \`ProcessTree\` получает лимит только для анализа, обычный экспорт не ограничивается новым лимитом.
- Отчёт не приравнивает \`uncertain\`/\`not_checked\` к доказательству сохранности. Шрифт, формулы без cache, растровые PDF-изображения, семантика и многие форматы честно остаются в зоне «не проверено».
- Пользовательские имена и findings в comparison JS вставляются через \`textContent\`; необработанные документы не загружаются в iframe.
- Машинные доказательства v19: self-hosted #40197557880 SUCCESS, два native recipes PASS, offscreen Qt PASS, frozen analysis/PDF/image workers PASS. Данные получены из опубликованного evidence, самостоятельно повторного запуска не выполнялось.

4. Повторить единые регрессии source/Windows/Qt + FULLTEST реальных 510 и выборочные реальные Office-сравнения (DOCX/PPTX/XLSX/ODF/HTML), 2 темы, Excel merger, BLACK.BOX, guarded negative fixtures; UI установленного EXE отдельно.

Это source/evidence tech review; доказательств новых user-data потерь нет, но условные пути false proof и UX/persistence требуют дополнительных тестов.
