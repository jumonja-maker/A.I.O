### Ограничение памяти восстановления

При перезапуске загружается не больше `max_jobs` наборов метаданных. Остальные папки остаются на диске и отражаются в `pendingRecoveryFolders`. После сохранения/удаления доступных заданий можно получить следующие. Тест восстанавливает три задания при лимите два и проверяет доступность третьего после освобождения слота.

Ссылки и Windows reparse points исключаются при спасении. Проверка сделана совместимой с Python 3.11: `Path.is_junction()` из Python 3.12 не требуется. Источник не включается в спасаемые выходы, конвертация автоматически не возобновляется.

### Подготовка 1 000 файлов

До патча загрузка каждого исходника в локальный сервер последовательно ожидала предыдущую HTTP-операцию. Теперь используются **до четырёх локальных передач**, с ожиданием завершения всех начатых передач перед освобождением неудачной подготовки. Preflight начинается после всех загрузок. Порядок плана и одиночная нативная очередь не меняются.

Обновление индикатора загрузки ограничено по частоте, с точным конечным счётчиком. Никакого поиска пар в интернете нет.

Регрессия с 21 передачей подтверждает максимум четыре одновременно, единственный preflight после завершения всех передач и отсутствие автоматического `/start`. DOM/HTTP сценарий 1 000 файлов прошёл приблизительно за 17 с в отдельном прогоне. Это **подготовка + синтетические экспорты**, не скорость обработки 1 000 реальных документов.

### Дополнительная ошибка карточек

Когда часть исходников не входила в подтверждённый план, backend возвращал статусы только допущенных файлов. UI сравнивал их количество со всеми добавленными карточками и отклонял обновление. Допущенные карточки оставались «В очереди» после завершения экспорта.

Теперь обновляется переданное подмножество; ранее помеченные пропущенные файлы сохраняют свой статус. DOM-проверка включает недопущенный DOCX и два допущенных исходника. После подтверждённого сохранения зелёная галочка исчезает, подпись «Сохранено» остаётся. Ошибки/пропуски сохраняют отдельные символы.

## Проверка структуры: контракт и стоимость

По умолчанию выключена. Включается перед очередью; во время начавшейся конвертации её режим не меняется. Она не добавляет движок конвертации: экспортирует установленный LibreOffice. Добавлен `pypdf>=6.10,<7` как считыватель PDF; он требуется при подготовке окружения/сборки, а не скачивается приложением при конвертации. Если считыватель недоступен, диагностика сообщает `not_checked`.

Базовая структура исходника читается один раз на файл, результаты — по одному на направление. XML не удерживается полным деревом. По умолчанию диагностический бюджет — 64 MiB данных и 8 с; внешний контроллер завершает зависший процесс. На POSIX дополнительно ограничено адресное пространство дочернего анализатора 768 MiB. Эквивалентный Windows memory ceiling пока не установлен: там подтверждены код владения процессом и дедлайн, а реальный RSS ещё надо измерить.

Бюджет анализа **не является ограничением размера конвертации**. Если анализ не уложился, результат конвертации остаётся доступен, качество помечается непроверенным.

Значения статуса:

- `not_checked`: недостаточно сопоставимых данных, неподдерживаемый тип, тайм-аут или другая неопределённость.
- `checked_subset`: сопоставлена только указанная часть структуры; это не сертификат качества.
- `risks_found`: найдено расхождение, которое требует просмотра; нативный файл не удаляется и не скрывается.

Уменьшение количества элементов — признак риска. Изменение текстового digest — признак отличия извлечённого текста, а не доказательство исчезновения изображения букв. EPUB может добавлять оглавление и менять порядок частей. Преобразование формул в PDF/CSV закономерно лишает редактируемости; это отражается отдельным ограничением формата.

Известные границы: сложные формулы, полнота многолистовых значений, динамический HTML, все варианты CSV-кодировок/локали, встроенные документы и растровые пиксели требуют следующих проверок. Их нельзя помечать пройденными на основании одного счётчика.

## Три старые проблемы: что теперь доказано

### Сохранение во время длинной очереди

В production `owns_path()` теперь проверяет фиксированный служебный корень без получения общего lock Guard на Qt GUI thread. Это убирает конкретный путь ожидания интерфейса за большим snapshot/журналом/подтверждением сохранения.

Тест удерживает lock другого потока и проверяет быстрый ответ `owns_path`. Реальные Qt Widgets save-slots, очередь сигналов, немодальность и защита от повторного picker прошли. Стресс 7 000 задач сохраняет ранний snapshot, пока появляется поздний результат, и подтверждает, что поздний файл не считается сохранённым.

**Историческое зависание настоящего Windows WebEngine не объявлено закрытым.** Нужны воспроизведение на NIKITA с видимым окном и контроль обоих event loops, а также диска и дерева процессов.

### ODC: standalone и встроенный контекст

Заново получены из исходного тестового набора три ODC уровня 1–3. Хеши записаны в JSON; исходники не изменялись. В каждом `mimetype=application/vnd.oasis.opendocument.chart`, присутствует ссылка на родительский контекст `..`. Это полезная гипотеза о зависимости от контейнера, **не доказанная причина зависания**.

На локальном LibreOfficeDev 26.8:

| Проверка | Результат |
|---|---|
| Нативный импорт LOK | Успешно загружает OTHER-модель |
| Новый Guard | Уточняет ChartDocument по уже загруженной модели + точному ODF mimetype/структуре, независимо от расширения |
| Нативный реестр | Для `com.sun.star.chart2.ChartDocument` зарегистрирован экспорт ODC; PDF для этой модели отсутствует |
| Прямой CLI ODC→PDF без Guard | Все три контрольных вызова прерваны после заданных 12 с |
| Guard ODC→PDF | Не запускает эти неподтверждённые экспорты |

Обычный OTHER и произвольный `.odc` не превращаются в ChartDocument только по имени. Формулы продолжают проверяться отдельно. В Windows используется реальная UNO-модель; текущий Linux результат не заменяет её испытание.

**Не сделано:** автоматическое оборачивание ODC в Writer/Draw и подмена желаемого результата. Это изменило бы смысл преобразования. Экспорт встроенной диаграммы внутри настоящего документа-контейнера всё ещё требует отдельного образца и Windows-проверки.

### ODT уровня 3 → CSV/SVG/EPUB

Тот же исходный ODT проверен прямым CLI и Guard. Базовая копия и байты пользователя сохранены.

| Направление | Прямой LibreOffice | Guard |
|---|---|---|
| CSV | `no export filter` | Та же причина; теперь `NATIVE_EXPORT_FILTER_UNAVAILABLE`, без ложного успеха |
| SVG | Native Writer store завершается ошибкой | Та же нативная ошибка; зарегистрированный `writer_svg_Export` остаётся разрешённым, риск показан и для LOK text-family proof |
| EPUB | Создан реальный EPUB | Создан EPUB; таблица/изображение обнаружены, отличие текста помечено для просмотра |

Наличие записи в реестре не гарантирует работоспособность выбранного default CLI exporter для каждого документа. В частности, зарегистрированные Writer text-фильтры могут иметь CSV среди расширений, но стандартный CLI выбор в этом окружении не находит исполняемый CSV-фильтр. Нельзя скрыть это общей надписью «ошибка AIO»; нельзя и выдавать TXT с новым расширением за проверенную таблицу CSV.

**Эти результаты не исправляют LibreOffice.** Windows UNO, фактическая полезность текстового CSV-экспорта и Writer SVG остаются пунктами приёмки. Форматы не удалялись из общего каталога и не закрывались чёрным списком по расширению.

### Excel: измерение памяти, не рекламный тест скорости

Три источника по 4 000 строк; всего 12 000 строк × 8 столбцов. Старый и новый код запускались в отдельных Linux-процессах, с tracemalloc и одинаковой проверкой результата.

| Показатель | QA-база | Патч |
|---|---:|---:|
| Пик Python allocations | 33 774 363 B | 20 523 528 B |
| Python allocations после merge | 26 290 811 B | 634 966 B |
| Whole-process max RSS, Linux ru_maxrss | 119 304 KiB | 95 652 KiB |
| Время с tracemalloc | 19,39 с | 20,31 с |

Пик Python-памяти уменьшился на **39,23%**. В этом замере новый вариант немного медленнее. Размер XLSX также изменился из-за потоковой сериализации; логические значения и ширина строк совпали. Ускорение самого LibreOffice этим не доказывается.

### Где остаётся время нативной конвертации

Последний нативный 8-task pipeline занял около 109 с в очереди. Из отчёта: CLI процессы XLSX→CSV — 22,56 с, XLSX→TSV — 26,96 с, CSV→PDF — 53,31 с. Большая часть ожидания находится **в настоящих процессах LibreOffice Calc**, а не в новом структурном сравнении. В этой Linux-среде применяется `native_cli`; `officeStarts=0` не означает отсутствие CLI-процессов — счётчик относится к управляемой тёплой сессии.

Патч ускоряет передачу/подготовку партии и снижает память Excel; общего ускорения нативного Calc на Windows пока не заявляется. Там надо сравнить холодный CLI и штатную тёплую UNO-сессию на одинаковых исходниках и фильтрах.

### Почему менялись старые тесты

- POSIX fake-soffice теперь создаёт PDF с правильной сигнатурой: новый primary contract из PR #23 обоснованно отвергал `b'fixture'` как PDF. Реальный валидатор не ослаблялся.
- Повреждённый журнал теперь позволяет спасти неиндексированные выходы; старые ожидания «виден один/не видны никакие» заменены проверками полного спасения, недолговечности и запрета автоматического удаления.
