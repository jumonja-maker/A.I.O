# Converter Guard v0.3 — индивидуальный план и повтор ошибок

Продолжение [PR #5](https://github.com/jumonja-maker/A.I.O/pull/5),
основа `d0fa74afb9fc44a469047c950b788e36d73a2916`.
Это отдельный патч библиотеки для 00AIO. Guard по-прежнему не импортируется
основным сервером и не включается в интерфейсе. Старый PR #2 не требуется.
Для интеграции нужны изменения #5, затем этот патч. Восстановление изображений
и значка приложения передаётся независимым PR.

## Что изменено

| Сценарий | Поведение |
|---|---|
| Разным файлам нужны разные форматы | `plan` задаёт направления отдельно для каждого файла |
| Пользователь использует прежний общий список `formats` | Старый вызов сохраняет поведение |
| Одна пара завершилась ошибкой | `retry_plan` возвращает только неудачные направления и необходимые исходники |
| Часть файлов была отменена | Они попадут в повтор только при явном `include_cancelled=True` |
| Успешный результат уже получен | Повтор не пересоздаёт и не удаляет его |
| Состояние очереди не изменилось | `since_revision` возвращает краткий ответ; HTTP возвращает 304 без тела |
| Нужен журнал | `include_trace=True` / `trace=1` явно запрашивает полное состояние |

Например, Writer → PDF + ODT, BMP → PNG, Calc → XLSX + CSV дают пять native-вызовов.
Общий список из пяти форматов для трёх исходников дал бы пятнадцать попыток.
Это уменьшение лишней работы; скорость одного native-экспорта патч не меняет.

Формат не отсекается по типу исходника или каталогу. Любое структурно корректное
расширение передаётся штатному LibreOffice. Входные байты, настройки экспорта,
изображения и качество документа этот патч не переписывает. Ограничения размера,
числа файлов, страниц и времени по умолчанию не добавлены.

## Контракт библиотеки

```python
job = guard.create(
    [{'id': 'writer', 'name': 'contract.docx', 'size': writer_bytes},
     {'id': 'image', 'name': 'picture.bmp', 'size': image_bytes}],
    plan=[{'fileId': 'writer', 'formats': ['pdf', 'odt']},
          {'fileId': 'image', 'formats': ['png']}],
)
# upload() для каждого исходника, затем start() — как в v0.2.
state = guard.status(job['jobId'])
next_state = guard.status(job['jobId'], since_revision=state['revision'])
# {'jobId': '...', 'revision': 1, 'unchanged': True} при отсутствии изменений.
```

`plan` содержит ровно одну запись на каждый переданный исходник. Неизвестные и
повторные ID, пропущенные файлы и пустые списки форматов отклоняются до создания
временного каталога. Порядок исходников сохраняется; повторные форматы
дедуплицируются. Порядок записей плана не переставляет отображаемые файлы.
`plan` нельзя смешивать с общим `formats`.

После завершения:

```python
retry = guard.retry_plan(old_job_id)
if retry['requiresUpload']:
    new_job = guard.create(retry['files'], plan=retry['plan'])
    # Явно загрузить только перечисленные исходники и запустить новое задание.
```

Это метаданные для подтверждаемого пользователем действия. Они не запускают
конвертацию, не читают пользовательский диск и не обещают исправить неподдерживаемый
формат. Временные исходники удаляются после последнего направления, как в v0.2;
повтор требует загрузки исходников. Host сопоставляет ID с первоначально выбранными
файлами, проверяет доступность и предлагает изменение формата при необходимости.
Весь исходный документ не удерживается ради потенциальной повторной попытки.
План для работающего/незапущенного задания возвращает `JOB_STATE` / 409.
Для полностью успешного задания `files` и `plan` пусты, `requiresUpload=False`.
Ошибки упаковки ZIP не являются ошибками native-конвертации и не требуют
повторной обработки успешных пар: сохраните отдельные outputs.

## HTTP

Namespace и авторизация остаются из v0.2: `/api/converter-guard`, loopback,
`X-AIO-Token`, проверка Host/Origin. API подключается только явно.

- `POST /jobs`: передать `files` и один из `formats`, `formatId`, `plan`.
  Поле `plan: null` и смешение способов возвращают явную ошибку.
- `GET /jobs?job=ID`: полный JSON и `ETag: "ID:revision"`.
- Следующий GET с `If-None-Match` этого же задания возвращает 304 без тела,
  если данные не изменились. Клиент оставляет предыдущее состояние и не вызывает
  `response.json()` на 304. При изменении — 200, новый ETag и полный JSON.
- `GET /jobs?job=ID&trace=1` всегда возвращает полный ответ с журналом.
- `GET /retry-plan?job=ID`: план только ошибок.
- `GET /retry-plan?job=ID&includeCancelled=1`: также отменённые направления.

ETag другого задания или некорректное значение не скрывают обновления: возвращается
полный ответ. ETag не заменяет авторизацию. `Cache-Control: no-store` сохраняется;
клиент хранит текущий ETag самостоятельно. Схема v2 расширена полем `revision`,
существующие клиенты без условного опроса продолжают получать полный JSON.

Каждое публично значимое изменение состояния увеличивает revision, включая
готовность результата, упаковку, подтверждение сохранения и окончание worker.
Последнее отдельно проверено: `finished=True` не теряется при быстром опросе.
Счётчик монотонный для одного задания и живёт в памяти этого процесса.

## Расход ресурсов

При неизменном состоянии не создаются список файлов/outputs, snapshot и JSON.
Проверка revision и ответ имеют постоянный размер; существующая проверка
удаления заброшенных заданий сохраняется. Полный изменившийся status всё ещё
линейный по числу пар; это не push-подписка и не дельта-протокол.
Журнал остаётся ограниченным 512 событиями. Новых таймеров, worker-пулов,
анализаторов документов, превью и дополнительных фоновых циклов нет.
Метаданные retry строятся по запросу и линейны по числу пар.
